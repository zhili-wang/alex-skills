# Clarify — 需求澄清

> 在动手写方案之前，把模糊的需求搞清楚，避免因理解偏差导致返工。

**Announce:** "使用 clarify skill 进行需求澄清"

## Iron Law

```
NO SPEC WITHOUT CLARIFY（中复杂变更）
```

中复杂变更跳过澄清直接写方案 = 不确定的需求变成确定的返工。

## 行为准则（受 Karpathy 启发）

> 源自 [Andrej Karpathy 对 LLM 编码陷阱的观察](https://x.com/karpathy/status/2015883857489522876)：
> "模型会代你做错误假设，然后不假思索地执行。它们不管理自身的困惑，不寻求澄清，不呈现矛盾，不展示权衡。"

### 不假设，呈现权衡

- **说出你的假设**：扫描需求时，如果某个理解基于未验证的推断，明确说出来
- **呈现全部解读**：如果需求有多种理解方式，**全部列出**，让用户选择，不要默默选一种
- **每个选项附带 tradeoff**：A 方案快但扩展性差，B 方案复杂但灵活 — 把权衡说清楚

### 简洁克制

- **不过度追问**：不追问小概率边缘场景（"万一数据库挂了怎么办"），聚焦影响实现的真正模糊点
- **不推测需求**：不追问推测性功能（"将来可能需要..."），只澄清当前需求范围内的
- **一个问题一个决策点**：不要在一个问题里堆叠多个维度

### 精准修改

- **更新需求文档时只改相关章节**：澄清数据模型 → 只改数据模型章节，不"顺手优化"交互描述
- **澄清记录只追加**：不重写已有的清晰内容，不"改进"已确认的需求描述
- **已清晰的内容不动**：标记为"清晰"的类别，不要为了显得全面而重复提问

### 目标驱动

- **每个问题绑定一个决策**：提问前先想清楚"这个答案会改变什么实现？"
- **可验证的成功标准**：澄清完成 = 8 个类别都有明确状态（清晰/已解决/延后），没有无依据的"清晰"

---

## 触发条件

- 中复杂前端变更，需求描述存在模糊点
- 需求源（禅道/飞书/文档）获取后、技术方案生成前
- 需求描述中有未明确的交互、数据、边界等关键信息

---

## 核心流程

```
扫描需求 → 生成问题队列 → 逐一提问 → 增量更新 → 覆盖度摘要
```

---

## Step 1: 模糊性扫描

按前端模糊性分类法对需求进行结构化扫描，对每个类别标记状态：**清晰 / 部分 / 缺失**。

**标记"清晰"前，先说出你的假设。** 如果某个类别看起来清晰，但实际上是你在替需求方做推断（"用户应该需要..."），标记为"部分"而非"清晰"。

仅对"部分"或"缺失"的类别生成候选问题。

### 八大类别检查清单

**1. 功能范围**
- 核心用户目标是否明确？功能边界（什么不做）？
- 用户角色/权限是否有区分？页面是否需要权限控制？
- 数据是只读还是可编辑？是否需要批量操作？

**2. UI/UX 交互**
- 关键用户操作流程是否完整？错误/空/加载状态是否定义？
- 表单校验时机？空列表展示？操作反馈形式（Toast/Message/Dialog）？
- 是否需要骨架屏？筛选条件是否可保存/重置？

**3. 组件选型**
- 是否已确定使用哪个组件？是否需要新建组件？
- 表格是否需要虚拟滚动？选择器单选还是多选？
- 日期选择器范围？是否需要自定义组件？

**4. 数据模型**
- 实体字段和类型是否完整？实体间关系是否清楚？
- 分页方式（前端/后端）？枚举值映射表？
- 是否有前端计算字段？数据是否需要前端缓存？

**5. API 对接**
- 接口地址、请求/响应类型是否明确？错误码处理方式？
- 排序字段和方向？模糊搜索支持？文件上传限制？
- 是否需要加密参数？401 跳转逻辑？

**6. 业务规则**
- 关键业务逻辑是否清楚？状态流转是否有定义？
- 状态变更后是否自动刷新？是否有操作确认弹窗？
- 是否有操作日志/审计需求？

**7. 边界情况**
- 异常输入、并发操作、数据一致性如何处理？
- 超长文本截断？表格列数过多？网络断开草稿保存？
- 快速重复点击防抖？浏览器兼容性？

**8. 非功能质量**
- 性能量化目标？首屏加载时间？大数据量渲染性能？
- 是否需要键盘导航、国际化、SEO？敏感信息脱敏？

## Step 2: 问题优先级排序

从候选问题中选取**最多 5 个**，按 `影响 × 不确定性` 排序：

- **高影响**：会影响架构、组件选型、数据模型、API 对接、安全合规
- **高不确定性**：需求源中未提及、或描述模糊

**跳过规则：**
- 需求源已明确回答的 → 不问
- 纯风格偏好（不影响实现）→ 不问
- 更适合放到技术方案阶段的技术选型 → 标记延后，不问
- 小概率边缘场景（发生概率极低或与当前需求范围无关）→ 不问
- 推测性需求（"将来可能需要..."）→ 不问，当前需求范围外
- 一个问题可覆盖多个类别 → 合并为一个问题，不重复追问

---

## Step 3: 逐一提问

**一次只问一个问题。** 不要一次展示多个问题。

每个问题必须先说明 **"为什么这个答案会影响实现"**（一句话），再给出选项。

### 多选题格式（优先）

```markdown
> 这个决定影响：{一句话说明对架构/组件/数据模型/API的具体影响}

**推荐:** 选项 A — {推荐理由}

| 选项 | 说明 | 权衡 |
|------|------|------|
| A | {说明} | {一句话：选了A意味着什么，放弃了什么} |
| B | {说明} | {一句话} |
| C | {说明} | {一句话} |
| 自定义 | 提供你自己的简短回答（≤5字） | — |

回复选项字母、说"推荐"接受推荐、或提供自定义答案。
```

**关键：每个选项的权衡列必须填写**，不能为空。让用户做的是**知情决策**，不是盲选。

### 简答题格式（无法多选时）

```markdown
> 这个决定影响：{一句话说明对实现的具体影响}

**建议:** {建议答案} — {建议理由}

格式：简短回答（≤5字）。说"建议"接受建议，或提供自己的答案。
```

### 回答处理

- 用户回复"推荐"/"建议"/"yes" → 使用推荐/建议作为答案
- 用户回复选项字母 → 使用对应选项
- 用户回复其他内容 → 验证是否有效，模糊时追问（不计入问题数）

---

## Step 4: 增量更新需求文档

每个答案确认后，**立即**更新到需求文档中：

0. **输入类型检测**（仅在首个答案时执行一次）：
   - 若用户提供了文件路径 → 继续后续步骤
   - 若用户以自由文本描述需求（无文件路径）→ 先询问用户是否创建需求文档，默认路径 `docs/requirements/clarify-YYYY-MM-DD.md`，确认后方可继续
1. 确保需求文档中有 `## 澄清记录` 章节（无则创建）
2. 在其下创建 `### Session YYYY-MM-DD HH:mm` 子标题（含时间戳，防止同日多次执行产生重复头）
3. 若已存在同日 Session 头，**直接在其末尾追加**新的 Q&A 行，不重复创建子标题
4. 将澄清内容应用到需求文档 **最相关的章节**（精准修改，不碰无关章节）：
   - 功能模糊 → 更新功能需求
   - 交互流程 → 更新交互规格
   - 数据模型 → 更新数据结构
   - 边界情况 → 添加边界条件
   - 非功能约束 → 添加可量化指标
5. **不要"顺手优化"已有清晰内容**：已有的文字只要不和新答案冲突，保留不动
6. **写入文件后继续下一个问题**（防止上下文丢失）
7. **验证**：写入后回读修改的章节，确认新内容和原有内容不冲突
   - **若检测到冲突**：撤销本次写入（恢复原文），向用户展示冲突内容，请求确认后再写入
   - **若写入成功**：确认无误后继续下一个问题

---

## Step 5: 覆盖度摘要

提问结束后，输出覆盖度摘要：

| 类别 | 状态 |
|------|------|
| 功能范围 | 已解决 / 延后 / 清晰 / 未决 |
| UI/UX 交互 | ... |
| 组件选型 | ... |
| 数据模型 | ... |
| API 对接 | ... |
| 业务规则 | ... |
| 边界情况 | ... |
| 非功能质量 | ... |

- **未决**：仍有高影响模糊性，建议再次 clarify 或补充需求源
- **延后**：更适合技术方案阶段解决，可继续
- **已解决/清晰**：无需额外处理

## 红旗 — 停下自检

- 跳过模糊性扫描直接开始提问 → 必须先扫描，否则遗漏关键模糊点
- 一次问多个问题 → 用户无法专注思考每个问题
- 不提供推荐选项 → 增加用户认知负担，降低效率
- 选项没有 tradeoff 说明 → 用户在做盲选，不是知情决策
- 答案没有立即写入需求文档 → 上下文丢失风险
- 问了 5 个问题但没有涉及核心模糊点 → 排序逻辑有误
- 在已有清晰内容上"顺手优化" → 越界修改，引入新风险
- 替用户做了假设而没有说出来 → 你以为是"清晰"，实际是臆断
- 追问小概率或推测性场景 → 过度澄清，浪费决策精力
- 写入后检测到冲突但未撤销 → 错误修改静默传播，下游方案基于错误需求编写
- Session 头未用时间戳 → 同日重复执行产生歧义记录
- 自由文本输入未创建需求文档 → 澄清答案无落盘路径，上下文溢出即丢失

## 常见借口

| 借口 | 现实 |
|------|------|
| "需求很清楚，不用澄清" | 前端需求返工率最高，"清楚"通常是你在替用户做假设 |
| "5 个问题太多了" | 5 个问题 < 5 次返工，澄清成本远低于返工成本 |
| "先写方案，有问题再说" | 方案写完再改 = 推翻重来，澄清后写 = 一次到位 |
| "这个放到实现时再决定" | 实现时决定 = 开发者按自己理解做 = 偏离需求 |
| "简单变更不用澄清" | 简单变更确实可以跳过，中复杂变更必须澄清 |
| "这个问题太小了不需要权衡" | 没有不需要权衡的决策，只是你没说出来 |
| "顺便把这个也问了吧" | 超出当前需求范围的追问 = 推测性需求蔓延 |
